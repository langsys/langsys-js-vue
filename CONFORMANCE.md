**What surfaced while re-rowing against 8.3.0** — each item came from running code against the contract double or the shared vectors:

1. **GATE-10's readers are the DOM hosts, and a bare `t()` is outside them.** `<Translate>` and `<Phrase>` hand the core their host, and the core's ancestor walk suppresses both lanes under a `data-ls-resolved` ancestor; `useT()` under the same ancestor registers, measured against the double. Spec 8.2.10 makes that the rule's negative control: a `t()` argument is source text the app supplies, and GATE-9 is the gate for `t()`.
2. **HINT-13's hook closes a second Vue shape.** Besides the persistent layout, vue-router reuses a route component when only a param changes, and a child of it that reads nothing from the route never re-renders. With `syncNavigation(router)` its miss is stored for the new URL; without it, nothing is.
3. **Server rendering runs through the core's request scope, and three things surfaced wiring it.** A Nuxt plugin cannot wrap Nuxt's render, and `scope.enter()` called inside an awaited async function after its own `await` — the plugin shape — does not isolate the request: interleaved Italian and German requests served the Italian one German, three runs of three. So the Nuxt path hands the scope to the request's own Vue app (`provideRequestScope`), which needs no async context. The core's `currentlyLoadedLocale` and `sTranslations` did not follow the scope at first (Reviewer's vector read `Prezzi|de|Preise`); at 32f99e1d they do, and the vector reads `Prezzi|it|Prezzi` inside the scope and `Preise|de|Preise` outside it. The composables also read a scope provided to the app, which has no async context. And every server render left one subscription per composable on the core's signals — 50 renders, 50 opened, 0 released — because Vue never stops a server component's scope; the composables no longer subscribe on the server.
4. **The message render decision is the core's.** `useServerMessage()` is a reactive wrapper over `renderServerMessage()`; this binding reads no catalog of its own (probe p08: 0). Entries are read only from the key or resolver the app configures, beside the framework's own error body, which stays untouched — the Inertia page case asserts it.

5. **The migration config and snapshots pass through untouched.** `legacyKeys` reaches the core through the `init` override as the app wrote it: a key resolves to its source value, and a vue-i18n pipe plural renders by count only because its `format` arrived. This binding's code never names the option (probe p37: 0). A snapshot loads through the forwarded `loadSnapshot`, and a refusal reaches the caller with its reason; the core takes a snapshot through that method, not through `init`.
6. **Rendering blocks without a DOM surfaced four core changes and one binding regression.** Wiring `<Translate>` and `<Phrase>` to the core's `renderBlock` against its unlanded build showed that `registerBlock` needed the host to honour GATE-10, that an app's `custom_id` needed its own option apart from an adopted stamp, that an untranslated block was marked resolved, and that registration is one-shot; all four landed in the core. Measured at the transport seam, a block nested under an ancestor that fell back to the core's DOM class was then sent twice, once by the ancestor's walk and once by itself; the binding now leaves it to the ancestor.
7. **A variable in a compiled template reaches `<Translate>` with its value already in the text.** `Hello {{ name }}` arrives as `Hello Ana`, and without help registers one phrase per user. The compiler transform has to run on the template root: Vue runs user transforms after its own, so a per-element rewrite leaves an unprefixed expression in a single-file component, and Vue's server compiler copies a component's slot children before a user transform reaches them, so a per-element rewrite served `You have 5 items` from a server build. Without the transform, Vue's own patch flags say which content was compiled from a variable, and such a block registers nothing. And blocks were not collected on the server at all: the components registered only on mount, which a server never runs; they now register inside the request scope.

> **`implemented` here means `n/a (pure)` or `contract` evidence.** HINT-13 and GATE-10 turn on what the server stores, and are proven against the vendored contract double. Every other owned rule governs an in-process property — the proxy's forwarding, the hydration latch, a rendered attribute, the order of events at hydration — which the double could neither prove nor disprove. Rules whose property depends on what the API answers, and that this binding does not touch, belong to the core and are delegated.

## Route changes — HINT-4 and HINT-13

`src/navigation-contract.test.ts` is HINT-13's own Test against the contract double: a read-only session whose key may report, so the double stores a hint for any page reported to it. Page components render only phrases the catalog translates, so a hint for a page can only come from the missing phrase the case places.

| Shape                                                     | with `syncNavigation(router)` | without                                               |
| --------------------------------------------------------- | ----------------------------- | ----------------------------------------------------- |
| persistent layout, plain `<RouterView>`, A→B              | hint stored for B             | —                                                     |
| persistent layout, `<KeepAlive>`, A→B                     | hint stored for B             | —                                                     |
| route-independent child of a page reused on `/p/1`→`/p/2` | hint stored for `/p/2`        | —                                                     |
| persistent layout, A→B                                    | —                             | **no hint for B**, although the double would store it |
| phrase only page A rendered, unmounted by A→B             | **no hint for B**             | —                                                     |

`src/route-reentry.test.ts` measures what Vue itself re-renders on navigation, with no hook: routed pages re-enter under a plain `<RouterView>` and under `<KeepAlive>`; a persistent layout, a `computed()` over `t()` in a cached page, and a route-independent child of a reused instance do not. Every case there first asserts that the URL moved and that a routed component re-entered at the new URL (M22, M23).

## Ranked gaps

Ranked by what each costs, not by rule order.

1. **Release wave — the dependency floor reads `^0.6.5`**, a core with none of the 838 surface this binding imports.
2. **VAR-3 — the core does not yet read value markers.** This binding passes them through; until the core reads them, a server-marked value splits its sentence. Nothing in this binding emits markers.
3. **Hand-written render functions and JSX register their values.** They carry no compiler signal; the README tells them to write `%name%` and params.
4. **MSG-12 — no end-to-end Inertia redirect here.** The page half is proven; the session half lives in the server binding.
5. **A block whose slot holds a component or `v-html` is served as source.** The sanctioned fallback: translated after mount. Crawlers see source for exactly those blocks.
